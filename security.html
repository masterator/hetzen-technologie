Our process, step by step

  1. Plan with security in mind

    Before we build, we list what information your project will hold, who should see it and what could go wrong. If it holds personal information, we plan for POPIA from day one: only collecting what's needed, and deciding how long to keep it.

  2. Set up accounts safely

    Hosting, domains and databases are registered in your name. Every admin account gets two-step verification. Each person and service only gets the access it needs, nothing more.

  3. Keep secrets out of the code

    Passwords, API keys and database keys are never written into the website code or sent in normal messages. They're kept in secure settings on the server. We scan the code to make sure none slip through.

  4. Lock down the data

    Database rules make sure each user can only reach their own records. We test this from the outside as three different people: a visitor who isn't logged in, a stranger with their own account, and the real owner. Only the owner should see the data.

  5. Check every add-on we use

    Modern apps use ready-made building blocks. We check them for known security problems, keep them up to date, and only load outside scripts with a tamper check, so a changed file is refused.

  6. Test against a recognised checklist

    We check your project against the OWASP Top 10, the world's most widely used list of web security risks (see below). For web apps we follow the OWASP Application Security Verification Standard (ASVS): Level 1 as our minimum, and Level 2 for systems holding sensitive or personal data. For mobile apps we follow the OWASP MASVS.

  7. Test on real devices

    We open your project in real browsers on phone and computer, try every form and button, and try wrong or unexpected input to make sure nothing breaks or leaks.

  8. Launch checklist

    HTTPS everywhere, test accounts deleted, admin two-step verification switched on, backups working, error messages that don't give away private details, and security settings checked by the hosting provider's own security tools.

  9. Handover and report

    You get a plain-language security report: what we tested, what we found, what we fixed and anything you need to do. We hand over every login securely and remove our own access when you ask.

  10. Aftercare

    On a support plan, we keep everything updated, re-run the security checks, and watch for problems. If something does go wrong, we tell you straight away and help you inform the Information Regulator and affected people, as POPIA requires.

The 10 risks we test for

These are the OWASP Top 10:2025 web application security risks, explained simply, with what we check for each.

A01

Broken access control

Can someone see or change data that isn't theirs? We test as a stranger and as a logged-out visitor.

A02

Security misconfiguration

Are any settings left open, like default passwords, extra permissions or debug pages? We switch off what isn't needed.

A03

Software supply chain failures

Is any add-on or library out of date or tampered with? We scan and update them, and verify outside files.

A04

Cryptographic failures

Is information encrypted when it travels and when it's stored? We use HTTPS everywhere and never store passwords in plain text.

A05

Injection

Can someone type something sneaky into a form to run code or read the database? We escape and check all input.

A06

Insecure design

Is the plan itself safe? We think through misuse before building, not after.

A07

Authentication failures

Can logins be guessed or bypassed? We use strong password rules, limits on attempts, and two-step verification for admins.

A08

Software or data integrity failures

Could an update or file be swapped for a harmful one? We check files before they run.

A09

Logging and alerting failures

Would we notice an attack? We make sure important events are recorded and problems raise an alert.

A10

Mishandling of exceptional conditions

What happens when something fails? We make sure errors fail safely and don't reveal private details.

Mobile apps

For Android and iOS apps we also check the eight areas of the OWASP Mobile Application Security Verification Standard (MASVS): how the app stores data on the phone, encryption, login, network connections, use of phone features, code quality, resistance to tampering, and privacy.

How we protect our own systems

We hold ourselves to the same standard. Our own business portal:

  • needs a password and a 6-digit authenticator code to sign in;
  • uses database rules that refuse your records to anyone else, even if they get our website's public key;
  • has been tested as a logged-out visitor and as a stranger, and both saw nothing;
  • clears customer data from the device when we log out;
  • has two-step verification on every admin account behind it (database and code hosting).

Being honest about limits: no system can be made 100% unbreakable. Our checks find and fix the common, serious problems that cause most real attacks. For systems handling payments, medical or highly sensitive data, we also recommend an independent penetration test by a specialist firm, and we'll help you arrange and prepare for it.

Common questions

Do I need to understand any of this?

No. You get a plain-language report and we explain anything you need to do. Usually that's just switching on two-step verification on your phone.

Is security extra?

No. The steps above are part of every project. Extra items, like an independent penetration test or ongoing monitoring, are quoted separately so you can choose.

Can you check a website or app someone else built?

Yes. We can run the same checks on an existing site or app and give you a report with what to fix, in order of importance.

What if something goes wrong after launch?

Contact us straight away on WhatsApp. On a support plan, we act immediately. We'll help you contain the problem, fix it and, if personal information was affected, notify the Information Regulator and your customers as the law requires.

How do I send you my passwords safely?

Don't send them in a normal WhatsApp or email. We'll invite you to give us access through the provider's own team or user settings, or show you a secure one-time sharing method.
